# C08: operation feedback and live logs

`ProgressBar.IsIndeterminate` animates a bounded segment inside the logical track.
`Value` remains a fraction from 0 to 1. `IsPaused` stops ticking without changing
the mode. Hiding or disabling an ancestor, detaching, and disposal remove the
animation from the owning Window; showing or reattaching resumes it. Theme
colors and the existing logical-to-framebuffer transform apply normally.

## Operation status

`OperationStatus` is an immutable presentation value: `Message`, `State`
(`Empty`, `Working`, `Completed`, `Failed`, `Canceled`), `Severity`
(`Information`, `Success`, `Warning`, `Error`), and optional fractional `Progress`.
A working status without progress uses the busy animation. Severity is written
alongside the message so it does not rely on color.

Native `StatusPanel.Status`, `Retry` and `Cancel` compose that value with
`Func<Task>` actions. `RetryAsync()` and `CancelAsync()` return observable tasks.
Retry is available for failed/canceled states; Cancel is available while working.
`IsProgressPaused` pauses indicator motion; `ShowProgress` controls only the
indicator's visibility, leaving the message and actions available.
Unavailable actions remain visible and disabled. Each action suppresses its own
duplicate invocation; an awaiting retry leaves cooperative Cancel available.
Replacing a callback, replacing status, detaching, or disposing prevents an older
action's completion/error from replacing newer presentation. Current action
errors are visible and retained in `ActionError`; direct callers also receive
the exception. Pointer/keyboard activation observes the task and presents errors.

Blazor `StatusPanel` takes the same `Status` and Task-capable `EventCallback`
parameters `Retry` and `Cancel`:

```razor
<StatusPanel Status="status" Retry="RetryAsync" Cancel="CancelAsync" />
<ProgressBar IsIndeterminate="isPreparing" Value="fraction" />
```

The application owns tasks, cancellation sources, status transitions and outputs.
There is no scheduler or toast service. Supply a real cancellation callback only
when the operation supports it. Converter's synchronous conversion API has no
cancellation parameter; this component does not make that API cancelable.

## Append-oriented logs

`LogBuffer` is frontend independent and thread safe. Construct it with immutable
`maxLines` and `maxCharacters` limits (defaults: 1,000 and 100,000). Use `Append`,
`AppendLine` and `Clear`. `Snapshot` is an immutable `LogSnapshot` containing
`Text`, monotonic `Version`, `StartOffset` and `ResetId`. `Changed` runs on the
producer's thread; non-Winter subscribers must marshal their own UI work.

Limits count UTF-16 code units and LF-separated lines, including a trailing empty
line; empty text has zero lines. Retention drops oldest complete lines first.
An oversized remaining line keeps a suffix, advancing the cut to a grapheme
boundary, so a retained suffix may be shorter than the character limit. A cluster
larger than the entire limit is discarded as a unit. `StartOffset` counts UTF-16
units removed from the current document. `Clear` empties it, resets this offset,
and advances `ResetId`.

Native `LogView.Buffer` and Blazor `LogView.Buffer` reference a caller-owned buffer.
A supplied buffer takes precedence over `Text`. Replacement resets inspection;
clearing Buffer restores the latest Text parameter. Attached views subscribe and
marshal worker notifications through their owning Window dispatcher. Detaching,
replacement and disposal unsubscribe; queued notifications from an obsolete
subscription cannot change the new view. A detached view catches up on attachment.
Neither frontend disposes the caller's buffer.

`LogView.Append`/`Clear` are UI-thread conveniences. A view without an explicit
buffer uses the default retention policy on Append. Existing `Text` remains an
exact whole-text replacement API, including large strings; it resets selection.
Appending to that snapshot activates the default retention bounds. Use a shared
`LogBuffer` for worker producers and explicit retention configuration.

`FollowTail` defaults to true. Appends and resize keep the latest output visible.
Wheel/scrollbar inspection, Home/Page keys, and text selection pause following.
`JumpToLatest()` or End resumes it. While paused, appends preserve the visible
line and selection. When old text is retained away, selection endpoints shift by
the discarded UTF-16 prefix and clamp to zero; a completely removed selection
collapses. The viewport shifts by discarded lines, clamping to the earliest
retained content if necessary. Clear resets selection and viewport but preserves
the follow policy. `SelectionStart`, `SelectionLength`, `SelectedText`, and
`ScrollOffset` expose the current native inspection state. Pointer hit testing
chooses grapheme boundaries. Native Copy/Select All remain available.

```razor
<LogView Buffer="logs" @bind-FollowTail="following" @ref="log" />
<Button Text="Jump to latest" OnClick="@(() => log?.JumpToLatest())" />

@code {
    private readonly LogBuffer logs = new(maxLines: 400, maxCharacters: 40_000);
    private bool following = true;
    private Marius.Winter.Blazor.Elements.LogView? log;
}
```

`FollowTailChanged` is authoritative when it has a delegate;
`OnFollowTailChanged` is the legacy fallback. Only one callback runs. Parameter
synchronization does not echo a user change. Explicit parent reset/rejection is
authoritative, including while a callback awaits. Set an empty EventCallback to
clear a callback, as with ordinary Blazor parameters. Native and component
reference commands require their owning UI thread; worker threads append to the
buffer instead.

## Playground modules and qualification

Native `Marius.Winter.Playground.Scenarios.OperationFeedbackScenario(Window)`
provides `Content`, `IDisposable`, and `IAsyncDisposable`. Its Window closing
handler cancels and awaits owned simulation tasks before native teardown.
Synchronous Dispose cancels and detaches; async disposal also awaits completion.
Blazor `Scenarios/OperationFeedback.razor` uses the same linked simulation and
implements async disposal. Both demonstrate a preview-pack installation with
empty/preparing/progress/completed/failed/retry/canceled states, disabled busy
starts, editable review notes, append logs, inspection/jump/clear and Reset.
Reset cancels and invalidates old runs. Pause/resume motion and hide/show progress
leave the operation and cancellation available. Both include small authored PNG, two-frame
GIF, and moving Lottie fixtures; the animations play during work. No files are
installed or converted. The simulation uses real cancellation checkpoints.

Host registration is an integration seam: instantiate the native scenario in the
playground host and render `<OperationFeedback />` in the Blazor host. C08 does
not edit the monolithic playground entry points.

Permanent tests cover buffer retention, Unicode boundaries, selection/viewport,
worker dispatch and subscription replacement, animation lifecycle, async action
identity, actual compiled Razor bindings and both modules' cooperative shutdown.
Owned-Xvfb scenario qualification covers actual pointer/keyboard input, first
frames, animation and selection pixels, light/dark appearance, larger text,
resize, and WM_DELETE_WINDOW. This establishes Linux/X11 software-renderer and
software-GL behavior only. The existing native Button larger-font sizing issue
and intermittent idle-CPU threshold remain separate open qualification limits.
Historical late-session GLX failures were addressed by the accepted Linux runtime
baseline; C08 preserves that runtime's process-owned GL procedure module and
ordinary per-session resource cleanup.
