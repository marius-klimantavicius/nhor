# C12: keyed lists and basic tables

`ItemController<TItem>` is a frontend-independent bounded collection and single-selection controller. Keys are nonempty, unique, ordinal strings from `KeySelector`; display names may repeat. `Items` exposes a read-only snapshot of `ItemSnapshot<TItem>` values. `SelectedKey` is the selection value, `SelectedItem` resolves its current item, and `Selection` carries both. `HasSelection` distinguishes no selection from a default-valued item.

`SetItems` snapshots and validates the entire replacement before changing state. `Configure(items, selectedKey)` applies data and an authoritative selection together. `Insert`, `Remove`, `Reorder` (a complete key permutation), and `Update(key, item)` retain surviving keys. An update cannot change its key; explicitly updating the same mutable reference still refreshes that row. Duplicate/null/empty keys reject the entire replacement. Removing, filtering out, or explicitly selecting an unmatched key clears selection; reintroducing a key does not restore it. Filtering belongs to the caller.

Use immutable item values when historical action values must remain immutable. Snapshot records retain the supplied `TItem` value/reference; the controller cannot deep-copy application objects. `ItemSelection<TItem>` and `ItemActivation<TItem>` capture the key and item at the interaction. Activation adds keyboard/double-click origin. Programmatic selection/data synchronization emits state/selection observation, never `UserSelectionChanged`. Native listeners run synchronously; attached views and controller mutations belong on their owning UI thread. There are no background loaders, application services, or async continuations in the controller.

## Native composition

```csharp
var items = new ItemController<Asset>(a => a.Id);
items.SetItems(assets);
var list = new ListView<Asset>(items,
    new ItemElementFactory<Asset>(
        a => new Label(a.Name),
        (element, a) => ((Label)element).Text = a.Name));
list.UserSelectionChanged += selection => ShowDetails(selection.Item);
list.Activated += activation => Open(activation.Item);
```

The caller owns the controller. Each view owns its native row containers and subscribes/unsubscribes independently, so list and table can share one controller/selection. `IItemElementFactory<TItem>` creates a native subtree and updates it only for a changed item or explicit `Update`. By default factory output transfers ownership to the view. Set `ownsContent: false` to borrow caller-owned output; removal/replacement/disposal detaches it for reuse. The caller then disposes it before the graphics session closes. Factories themselves and services captured by them remain caller-owned. Removed owned rows/content are disposed permanently. Reorder retains rows, content, focus, and selection for surviving keys. Removing a focused row moves focus to a surviving row at the nearest index, or clears it for an empty view.

`SetRowContent`/`SetEmptyContent` borrow by default, detach previous borrowed content, and support explicit ownership transfer. These are also the narrow attachment points for renderer-owned templates. `RowsChanged` fires after native reconciliation so slots can attach after an atomic attribute batch. `FindRow`, `FocusRow`, `EnsureVisible`, and `Viewport` provide native access. The viewport clips content and owns scrolling; this is not a panel loop in Blazor.

Tab visits each row and its focusable descendants in tree order. Row focus paints a distinct outline and ensures visibility without selecting merely on Tab entry. Up/Down/Home/End select and focus a row; Space selects; Enter activates. Primary pointer press on a row selects, and double-click activates once. Buttons/editors keep their own pointer and keyboard input, including Enter; their actions do not select or activate the row. A custom interactive descendant should be focusable. Descendant ScrollPanels also retain their input. List scrollbars never select/activate rows. Navigation is handled only when the row itself owns focus, so bubbled child keys do not become row commands.

`BasicTable<TItem>` uses the same controller and rows. Named `TableColumn<TItem>` values provide header, formatter or native cell factory, preferred width, minimum width, stretch weight, and optional comparer. A header click toggles real ascending/descending stable sorting of controller order. Equal values retain their current relative order. `ApplySort` is silent; `SortChanged` reports user header actions. Null clears the indicator and retains current order. Native callers reapply sort after data mutation if they want it maintained; the catalog does so. Column replacement validates names/metrics before applying it; replacing native columns rebuilds their cells. Header/row identity survives sorting.

Widths shrink proportionally from preferred widths to minima, then spare width goes to stretch columns. Below the sum of minima, trailing content is clipped; there is no horizontal spreadsheet layout. Each cell is clipped. Row height is measured from the current template/text, with a font-relative minimum. Sort indicators use `^`/`v`, which are present in the bundled font.

## Razor composition and binding

```razor
<ListView TItem="Asset" Items="assets" KeySelector="Key"
          @bind-SelectedKey="selected" OnActivate="Open">
    <ItemTemplate Context="asset">
        <Panel>
            <Label Text="@asset.Name" />
            <Button Text="Preview" OnClick="@(() => Preview(asset))" />
        </Panel>
    </ItemTemplate>
    <EmptyContent><Label Text="No matching assets" /></EmptyContent>
</ListView>

<BasicTable TItem="Asset" Items="assets" KeySelector="Key" Columns="columns"
            @bind-SelectedKey="selected" @bind-Sort="sort" />
```

`BasicTableColumn<TItem>` supplies named columns with `RenderFragment<TItem> CellTemplate`, formatter fallback, widths, and comparer. The table sorts a bounded snapshot of `Items` by its controlled `TableSort? Sort` before reconciling native rows. Use `SortChanged` or `@bind-Sort` to accept a sort; a parent may reject/reset it. No HTML/DOM is emitted. The actual catalog contains compiled Razor row and cell fragments.

`SelectedKeyChanged` is authoritative when it has a delegate; `OnSelectionChanged` is the legacy fallback only. `SortChanged` similarly takes precedence over `OnSortChanged`. Programmatic parameter synchronization produces no user echo. `SelectedItem`/`NativeView` expose the resolved native selection. Explicit parent resets/rejections are authoritative; increment `ResetVersion` to supersede queued input even when values are unchanged, and reset scroll to the top.

Equivalent method/target/receiver subscriptions recreated by compiled default or get/set binding survive ordinary unrelated renders. True callback replacement/clear, changed source/selector, explicit reset, changed key/item identity, and unmount invalidate old delivery. Selection and discrete activation/sort callbacks carry captured identities; activations/sorts are not coalesced. Multiple queued actions remain separate. Awaiting application callbacks do not write component state afterward or start another stale callback. The wrappers detach native subscriptions on disposal and never dispose caller services.

Razor slots are keyed by item key and cells by column key. Surviving native subtrees and focused descendants remain the same instances across insert/reorder/another-row update; removed templates are disposed once by the renderer. A single template root fills the slot; multiple roots stack vertically. Use an explicit Panel/Flex/Grid root for another arrangement. No shared renderer or Core focus change was needed.

## Asset catalog modules and limits

Native: `Marius.Winter.Playground.Scenarios.AssetCatalogScenario(Window)`, `Content`, `IDisposable`, with early `Closing` cleanup. Razor: `Marius.Winter.Blazor.Playground.Scenarios.AssetCatalog`. Both present the same eight assets, authored tiny SVG thumbnails, Filter/empty state, Reset, List/Table modes, selected details, Preview and activation results, insert/remove/reverse/rename/update-size controls, and real named-column sorting. Their shared sample data is compiled once in `Marius.Winter.Playground.Scenarios`; core controls have no application dependency. Host registration is deliberately separate: add the native module's `Content` to `ScenarioHost`, and render the Razor component in the corresponding host branch.

Permanent tests cover controller validation/identity/updates, native factory ownership, compiled bindings and keyed diffs, queued and awaiting callback lifetime, focused subtree survival, first-frame text/thumbnail/header pixels and focus pixels, and actual owned-X11 pointer/Tab/arrows/Enter/double-click/filter/scrollbar/resize/normal-close input. Both modules were exercised with light/default text, dark/22-unit text, and software Mesa GL. Qualification is Linux x64/glibc/X11/Xvfb/software Mesa only. Valid Unicode keys/text are preserved; the bundled font has incomplete Japanese/emoji glyph coverage. No new IME, high-DPI, other-OS, or hardware-GL claim is made.

This is a bounded list/basic table, with no virtualization, spreadsheet or cell editing API, grouping, frozen columns, tree grid, docking, or universal template engine. A TextBox can be composed in a row and keeps its input, but this does not establish a spreadsheet editing contract. No large-data performance claim is made.
