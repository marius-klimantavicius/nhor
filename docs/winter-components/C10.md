# C10 — SplitPane

`Marius.Winter.SplitPane` lays out two clipped content slots with an 8 logical-unit divider. `Horizontal` places First to the left of Second; `Vertical` places First above Second. Assign native `First` and `Second` Elements, or supply Blazor `First` and `Second` fragments:

```razor
<SplitPane @bind-Position="browserWidth" FirstMinimum="130" SecondMinimum="180">
    <First><ScrollPanel><Button Text="landscape.svg" /></ScrollPanel></First>
    <Second>
        <SplitPane @bind-Position="previewHeight" Orientation="Orientation.Vertical"
                   ResetPosition="180" FirstMinimum="80" SecondMinimum="70">
            <First><TextArea Text="Review the selected asset." /></First>
            <Second><LogView Text="@log" /></Second>
        </SplitPane>
    </Second>
</SplitPane>
```

Give the outer split space using the surrounding layout, for example `LayoutData="@(new FlexItem { Grow = 1, Basis = 0 })"` in a vertical Flex panel. A single fragment root fills its slot. Multiple roots form a vertical stack with 4 units of spacing; supply a Panel with its own layout for another arrangement.

## Geometry and resize policy

`Position` is the requested First extent, excluding the divider. Its default is 220. `VisiblePosition` reports the actual arranged extent. For an axis extent E, available pane space is `max(0, E - 8)`; the divider itself shrinks to E when E is below 8. Other dimensions fill the split.

When both minima fit, the visible extent is `clamp(Position, FirstMinimum, available - SecondMinimum)`. When they do not fit, First receives `available × FirstMinimum / (FirstMinimum + SecondMinimum)` and Second receives the remainder. Both sizes stay nonnegative. With zero minima the ordinary clamp applies. Child constraints may exceed the allocated size; each slot clips its content and hit testing to its rectangle. Use ScrollPanel or a scrolling editor inside a pane to make overflowing content reachable.

Resize and orientation changes preserve the requested Position, do not emit PositionChanged, and recompute the visible extent. Expanding therefore restores the previous request. A drag, arrow, Home/End, or Reset commits a new request clamped to the current visible range. Position, minima, and ResetPosition require finite nonnegative values; KeyboardStep requires a finite positive value. There is no ratio mode or docking behavior.

## Input and binding

Only the divider handles resizing; child editors, buttons, and scrollbars keep their input. Tab reaches the divider; focus/hover makes its line more prominent. Left/Right in Horizontal mode and Up/Down in Vertical mode move by `KeyboardStep` (default 10). Shift multiplies the step by five. Home/End select the current minimum/maximum; Enter and keypad Enter call Reset. `ResetPosition` defaults to 220. Native and wrapper `Reset()` are user actions and notify only on a change; assign Position for a silent parent reset. `FocusDivider()` uses the existing owning Window focus API.

Native `PositionChanged` describes user edits only. Blazor `PositionChanged` is authoritative when it has a delegate; `OnPositionChanged` is the compatibility fallback, never an additional notification. Parameter synchronization is silent, including an explicit rejection equal to the previous parent value. Scalar drag edits may coalesce within a UI turn. A queued edit cannot overwrite a newer parameter batch or target a disposed component, and awaiting callbacks have no state-writing continuation in the control. Application callbacks still own their own asynchronous work.

Native and Blazor `VisiblePositionChanged` separately observe geometry, including parent updates and window resize. This is useful for a requested/visible extent readout; it does not change the Position binding. Blazor geometry observations may coalesce.

The existing Window captures divider presses and releases capture on hide, disable, detach, disposal, or focus loss. The divider cancels its drag state on those transitions. Changing orientation, minima, or Position also cancels local dragging when the value changes. A no-op binding rerender preserves an active drag.

## Ownership and examples

Replacing or clearing native First/Second detaches the previous Element without disposing it. Dispose that detached content before its owning Window releases the graphics runtime. Content must be detached, live, and distinct from either slot's existing owner; invalid replacements leave the previous content intact. Disposing the split disposes its currently attached subtree. Blazor owns and disposes fragment subtrees when they are replaced or unmounted.

The matching modules are `Marius.Winter.Playground.Scenarios.ResizableWorkspaceScenario(Window)` (`Content`, `IDisposable`) and `Marius.Winter.Blazor.Playground.Scenarios.ResizableWorkspace`. They show browser/preview and nested vertical preview/log arrangements, asset selection, an editable review note, scrollbars, orientation changes, visible extent, preview replacement, hide/show, and parent Reset. The native scenario releases its attached and detached resources during Window closing as well as explicit disposal. Host navigation registration is performed by the integration owner; these modules do not edit either monolithic entrypoint.

Permanent tests live in `Marius.Winter.Tests/SplitPane*Tests.cs` and the independent Razor SDK project `Marius.Winter.SplitPane.Tests`. The latter compiles an actual `@bind-Position` fixture and checks renderer diffs, replacement, rejection, precedence, async removal, and scenario shutdown. Native tests exercise XTest pointer/keyboard/scrollbar/resize/capture transitions and first-frame clipping pixels on SW and GL. Run all window-creating tests in a privately owned Xvfb with inherited DISPLAY/WAYLAND_DISPLAY removed and software GL enabled. Qualification here is Linux/X11/Xvfb/softwareGL; hardware GL, other platforms, real high-DPI monitors, full font fallback, accessibility, and IME are outside this slice.
